日常開發中，我們很常用 Redis 來做快取（Cache）或是實作分散式鎖（Distributed Lock）。對我來說，它就是個存在記憶體裡、速度極快的 Key-Value 資料庫。

但你有沒有想過一個問題：**既然 Redis 的資料都存在記憶體裡，那萬一哪天伺服器突然斷電、或是服務被 K8s 重啟了，裡面的資料不就全沒了嗎？**

快取不見了可能頂多讓後端 DB 瞬間壓力變大，但如果裡面存了某些暫存的業務狀態，甚至是不可遺失的資料，事情就大條了。這也是我最近在研究 Redis 底層時，第一次深入接觸到 **AOF (Append-Only File)** 這個名詞。

這篇文章想用一個「只把 Redis 當 Cache 用的後端工程師」的視角，帶大家快速搞懂 Redis 是怎麼在背景幫我們保護資料的。

---

## AOF 是什麼？簡單來說就是「流水帳筆記本」

Redis 為了不讓資料因為斷電而消失，提供了兩種把資料寫入硬碟（持久化）的機制：RDB（快照）和 AOF。根據 [Redis 官方的 Persistence 指南](https://redis.io) 介紹，這兩者有著本質上的不同。

你可以把 **RDB** 想像成「定時幫整個資料庫拍一張庫存照片」，而 **AOF** 則是「櫃檯的點單流水帳」。

AOF 的運作邏輯非常直覺：
每當你對 Redis 下了一個會改變資料的指令（例如 `SET`、`DEL`、`INCR`），Redis 執行完後，就會把這個指令用純文字的格式，**追加（Append）** 到一個 `.aof` 檔案的最後面。

當 Redis 因為任何原因死機重啟時，它做的事情也很簡單：把這本「流水帳筆記本」從頭到尾重新執行一遍，記憶體裡的資料就全部還原了。

## 關鍵的效能權衡：什麼時候該把資料刷進硬碟？

身為工程師，我們直覺一定會想到：每次有寫入操作都要寫入硬碟，那 Redis 還快得起來嗎？

沒錯，這涉及到了 Linux 系統的 I/O 緩衝機制。Redis 收到指令後，會先寫到記憶體緩衝區（`aof_buf`），至於什麼時候才真正把資料「刷（fsync）」到硬碟裡，取決於 `appendfsync` 的設定：

*   **`always`**：每次有寫入指令就立刻刷進硬碟。這最安全，但效能會直接雪崩，通常不會有人這樣開。
*   **`everysec`（預設值）**：每秒鐘在背景刷一次硬碟。這是一個黃金平衡點，既能維持 Redis 的高效能，萬一真的遇到斷電，我們最多也只會遺失那一秒鐘內寫入的資料。
*   **`no`**：Redis 不主動刷，完全交給 Linux 作業系統決定。效能最好，但風險太高，不建議用在正式環境。

對我們平時只拿 Redis 當 Cache 的人來說，預設的 `everysec` 基本上就已經非常夠用且安全了。

## 檔案太大了怎麼辦？AOF 重寫機制 (Rewrite)

既然是流水帳，檔案一定會越來越大。假設我用 Redis 的 `INCR` 實作一個計數器，對同一個 Key 累加了 10,000 次，AOF 檔案就會記錄 10,000 條指令。但實際上，我們重啟時只需要最後那個最終結果（例如 `count = 10000`）。

為了避免硬碟被塞爆，Redis 內建了 **AOF 重寫（Rewrite）** 機制：
它會在背景 `fork` 一個子程序，直接去讀取當前記憶體裡的狀態，把前面那 10,000 條指令精簡成一條 `SET count 10000`，並寫入一個新的 AOF 檔案來替換舊的。關於重寫的詳細觸發條件（如 `auto-aof-rewrite-percentage`），可以參考 [Redis 官方的 Configuration 範例](https://redis.io)。

**⚠️ 這裡有個潛在的坑**：因為重寫需要 `fork` 子程序，並利用 Linux 的 Copy-on-Write 機制。如果你的 Redis 記憶體用量非常大，在重寫觸發的瞬間，記憶體用量可能會飆高。在規劃 Production 環境的伺服器規格時，通常不能把記憶體完全塞滿，要留有一些安全餘量。

---

## 現代 Redis 的標準解法：混合持久化

從 Redis 4.0 開始，官方推出了一個很聰明的模式叫「混合持久化」（在 `redis.conf` 中開啟 `aof-use-rdb-preamble yes`）。

它的邏輯是：在 AOF 重寫時，前半段先用 RDB 的二進位格式（體積小、載入快）把當前的記憶體狀態存下來；重寫期間新進來的增量指令，再繼續用 AOF 的純文字格式追加在後面。

這樣做最大的好處是，當伺服器重啟需要還原資料時，**速度會比純 AOF 快上非常多**，大大縮短了服務中斷（Downtime）的時間。

## 總結

以前總覺得 Redis 就是個記憶體資料庫，沒特別去想過它怎麼處理資料遺失的問題。這次梳理完 AOF 的機制後，總算明白為什麼在很多架構設計中，Redis 也能被拿來當作輕量級的持久化儲存來用了。

如果你的專案也有用 Redis，不妨去翻一下目前的 `redis.conf` 或是雲端託管服務（如 AWS ElastiCache）的設定，看看目前是開啟 RDB、AOF 還是混合模式。了解這些底層，在未來遇到效能瓶頸或是資料遺失的異常時，排查起來才會更有方向。
